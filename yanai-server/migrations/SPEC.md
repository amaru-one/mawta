## Purpose
The database schema, as one goose migration.

## Contents
- `00001_initial_schema.sql` — the whole schema in one file: ~2900 lines, 43 tables (plus `events`' `events_default` partition). Structure: `app` and `privacy` schemas (session-context helpers and privacy-audit views, no business data), the `yanai_app` non-owner role the service is meant to connect as, then table definitions grouped by area (tenants/users/memberships/teachers → academic structure → competencias/capacidades/criterios → sessions/attendance → grading schemes → evidence/scores/criterion scores → competency levels/conclusiones → notifications/events → jobs), each followed by its RLS policy, `comment on` text, indexes and trigger attachments. Ends with a full `-- +goose Down` that drops everything, including the `yanai_app` role.

## Inputs / Outputs
Applied with `goose -dir migrations postgres "$ADMIN_DATABASE_URL" up` against Postgres 16 — as the **superuser**, in one invocation, against an **empty** database. All three matter: `create extension` needs superuser, and the `alter default privileges` near the top only confers rights on tables created afterwards *by that same role*, so a split or re-roled run leaves `yanai_app` able to read nothing. Prod runs `pgvector/pgvector:pg16`, though pgvector itself is unused — nothing in this schema stores an embedding, and a plain `postgres:16` works.

## Conventions & Constraints
- **RLS pattern.** `app.current_tenant_id()` / `app.current_actor_id()` read `SET LOCAL app.tenant_id` / `app.actor_id`, returning NULL when unset — so a query that forgets to set the tenant returns nothing rather than raising or leaking. `app.enable_tenant_rls(p_table)` is the standard attachment: `ENABLE` + `FORCE ROW LEVEL SECURITY` plus a `tenant_isolation` policy `using (tenant_id = app.current_tenant_id())`. **FORCE matters**: it binds the table owner to the policy too, not just other roles, so "connect as the owner" is not a way to read across tenants on a table this helper touched. 38 tables use it; `tenants`, `users` and `events` carry hand-written policies instead, for 41 forced-RLS tables in all. Only `jobs` and `user_sessions` have no policy at all, both deliberately — `internal/db/db_test.go` asserts that list so a third never joins it unnoticed.
- **Four tables sit outside that pattern, each for a different reason.** `tenants` has no `tenant_id` column (it *is* the tenant), so its policy is `id = app.current_tenant_id()`. `users` has no `tenant_id` column either — deliberately not tenant-scoped, since it is the shared credential table — so its policy proves visibility through an existing membership instead: `exists (select 1 from memberships m where m.user_id = users.id and m.tenant_id = app.current_tenant_id() and m.deleted_at is null)`. A second, permissive `login_lookup` policy on `users` (and its twin on `memberships`) opens one narrow pre-tenant door: `app.current_tenant_id() is null and current_setting('app.auth_lookup', true) = 'on'`, set only by `internal/db.WithAuthTx` — the login and session-validation path, which has no tenant to set yet because resolving one *is* the point of the query. `jobs` carries a nullable `tenant_id` and **no RLS policy at all**: a job dispatched with no tenant (system-wide work) must be readable before any tenant is known, reached only through `db.WithSystemTx`. `user_sessions` also carries **no RLS policy**, for the same pre-tenant reason as `jobs` — a session row must be readable before `app.current_tenant_id()` can be set, since resolving it is how the tenant becomes known; its isolation is structural instead: the only reader is `internal/repo/auth.go`, always by exact `token_hash`, and a composite FK to `memberships (tenant_id, id)` makes a cross-tenant session row impossible to insert.
- **The connection role.** `00001` creates `yanai_app` with `login` (no password — set separately, see `docs/postgres-setup.md`/`DEPLOY.md`) and comments that the Go service must connect as it. `DATABASE_URL` does exactly that: `cmd/api` connects as `yanai_app`, a non-owner role scoped by RLS on every request. Migrations and `cmd/useradd`'s account-bootstrap (`internal/db.WithSystemTx`, which needs to write `users`/`memberships` before any tenant is known) both need real ownership/bypass privilege that `yanai_app` does not and should not have, so they connect separately via `ADMIN_DATABASE_URL`, as the `postgres` superuser — see `internal/config/SPEC.md` and `internal/db/SPEC.md`.
- **One person, one school.** `memberships_one_school_per_user` is a partial unique index on `memberships (user_id) where deleted_at is null and status <> 'revoked'` — a user may hold at most one active-or-invited membership at a time. Revoked memberships are excluded on purpose: a teacher who leaves one school must be able to join another, and a revoked row is history, not a live claim on the person. This is what makes "does this user have more than one membership" impossible rather than merely unhandled, so the login path needs no picker and no tie-breaking rule.
- **Role vocabulary.** `memberships.role` / `user_sessions.role` are `('teacher', 'student', 'supervisor', 'admin')`. All four are modelled — permission checks are written generically against `role` — but only `role = 'teacher'` may complete a login today (`domain.LoginEnabledRoles`); the other three exist so student and supervisor access can be turned on later by widening that map alone, with no further schema change. `role = 'student'` may exist on a `memberships` row while no `students` row is ever linked to a `users` row: students are not principals and have no login in this version.
- **`user_sessions`.** The browser holds an opaque 256-bit token in an HttpOnly cookie; the table stores only its sha256, so reading it never yields something that can impersonate anyone. `tenant_id`, `membership_id` and `role` are denormalised onto each session row so that one pre-tenant read yields the whole context; `user_sessions.role` is re-checked against the live membership on every request (in `internal/httpapi.sessionAuth`, not here), so a role downgraded after login takes effect immediately instead of waiting for the session to expire. Pruning expired/revoked rows is opportunistic — a best-effort sweep inside the login transaction — never a scheduled job, since nothing in this codebase runs on a ticker.
- **Append-only where a judgement or a mark is recorded.** `scores`, `criterion_scores`, `competency_term_levels`, `descriptive_conclusions` and `computed_grades` are superseded, never updated: a correction stamps `superseded_at` on the live row, then inserts the replacement with `supersedes_id` set. `scores` and `criterion_scores` each carry a `forbid_mutation` trigger that raises if any column but `superseded_at`/`deleted_at` changes on an existing row, so the convention is enforced by the database, not only by the Go callers that follow it.
- **`evaluation_criteria.capability_id`** anchors every criterio to a capacidad of the same competencia — a criterio cannot float free of the competencia's own structure. **`assessments.value_scale`** is `('numeric', 'rubric')`: numeric carries a positive `max_score` and an overall mark in `scores`; rubric carries no `max_score` and is valued only through per-criterio `criterion_scores`, and `assessments_rubric_not_internal` rejects a rubric assessment with `counts_toward_internal = true`. **`criterion_scores`** takes its own `value_scale` independently of the assessment's — a numeric mark needs the assessment's `max_score` (enforced in Go, `internal/repo.requireMaxScoreForNumeric`), an ordinal one resolves against the same `grade_scales` MINEDU levels `competency_term_levels` uses — and its FK to `assessment_criteria` means a criterio can only be scored if the assessment was actually tagged with it.
- **`grade_levels.cycle`** (`ciclo_i` / `ciclo_ii`) is meaningful only when `stage = 'inicial'`; every other stage leaves it null. It, together with `stage`, decides which `descriptive_conclusions.requirement` values are mandatory for a given student (see `internal/repo/SPEC.md`'s `classifyConclusionRequirement`).
- **`descriptive_conclusions`** and `competency_term_levels` both carry a required `academic_year_id` alongside a nullable `term_id` — a conclusión or a level can be asserted for a year without yet being tied to a specific term.
- Every table, column, non-obvious constraint and policy carries a `comment on`, in Spanish — this is the schema's own documentation of record, not a mock or a wiki page. A migration that adds or changes one of these without updating its comment is incomplete.
