## Purpose
The database schema, as goose migrations. `00001_initial_schema.sql` is the baseline (not an incremental history); every later file adds on top of it and is never folded back in.

## Contents
- `00001_initial_schema.sql` — the whole schema in one file: ~2981 lines, 72 tables. Structure: `app` and `privacy` schemas (session-context helpers and privacy-audit views, no business data), the `yanai_app` non-owner role the service is meant to connect as, then table definitions grouped by area (tenants/users/memberships/teachers → academic structure → competencias/criterios → sessions/attendance → grading → evidence/scores → notifications/events → jobs), each followed by its RLS policy, `comment on` text, indexes and trigger attachments. Ends with a full `-- +goose Down` that drops everything, including the `yanai_app` role.
- `00002_auth.sql` — real authentication: credentials on `users`, the role vocabulary collapsed to four values, and `user_sessions`. See its own section below.

## Inputs / Outputs
Applied with `goose -dir migrations postgres "$DATABASE_URL" up` against Postgres 16 (`pgvector/pgvector:pg16` in prod, though pgvector itself is unused since the transcription/embedding pipeline was dropped). Every environment is expected to run every migration in order from empty — there is no supported path that starts a fresh database at anything but `00001`.

## Conventions & Constraints
- **Migrations are append-only. Never renumber, rewrite or fold an existing file.** goose identifies a migration by the version number in its filename alone, never by content: renumbering a file — or rewriting one already applied in any environment — leaves `goose_db_version` claiming a version whose actual SQL never ran, and `goose up` then reports success while applying nothing. Every schema change is a new numbered file on top of `00001`, however much its content overlaps an earlier one. This matters most for the persistent production volume (`deploy/docker-compose.prod.yml`'s `pgdata`), which is migrated rather than re-created, so its recorded versions must keep meaning what they say.
- **RLS pattern.** `app.current_tenant_id()` / `app.current_actor_id()` read `SET LOCAL app.tenant_id` / `app.actor_id`, returning NULL when unset — so a query that forgets to set the tenant returns nothing rather than raising or leaking. `app.enable_tenant_rls(p_table)` is the standard attachment: `ENABLE` + `FORCE ROW LEVEL SECURITY` plus a `tenant_isolation` policy `using (tenant_id = app.current_tenant_id())`. **FORCE matters**: it binds the table owner to the policy too, not just other roles, so "connect as the owner" is not a way to read across tenants on a table this helper touched. 44 tables use it.
- **Three tables sit outside that pattern, each for a different reason.** `tenants` has no `tenant_id` column (it *is* the tenant), so its policy is `id = app.current_tenant_id()`. `users` has no `tenant_id` column either — deliberately not tenant-scoped, since it is the shared credential table — so its policy proves visibility through an existing membership instead: `exists (select 1 from memberships m where m.user_id = users.id and m.tenant_id = app.current_tenant_id() and m.deleted_at is null)`; the policy's own comment flags the ordering consequence — a membership must be inserted before the user row it names can be read back. `jobs` carries a nullable `tenant_id` and **no RLS policy at all**: a job dispatched with no tenant (system-wide work) must be readable before any tenant is known, so it is deliberately left open and reached only through `db.WithSystemTx`.
- **The connection role.** `00001` creates `yanai_app` (`nologin`) and comments *"The Go service must connect as yanai_app."* — but as of this writing the actual `DATABASE_URL` in `.env` and in `deploy/docker-compose.prod.yml` connects as `postgres`, the bootstrap superuser. This is a pre-existing gap between the schema's own stated intent and reality, not something any migration here has fixed; `00002`'s auth design (below) is deliberately built to keep working correctly regardless of which one is true, rather than depending on the superuser shortcut. See the root `SPEC.md` Open Questions.
- Every table, column, non-obvious constraint and policy carries a `comment on` — this is the schema's own documentation of record, not a mock or a wiki page. A migration that adds or changes one of these without updating its comment is incomplete.

## `00002_auth.sql` — real authentication

Added real login for the first time; before this, `internal/httpapi` trusted client-supplied `X-Tenant-ID`/`X-Actor-ID` headers outright (see `internal/httpapi/SPEC.md`).

**On `users`** — six new columns: `username`, `password_hash`, `password_changed_at`, `last_login_at`, `failed_login_count`, `locked_until`. `username` is unique on `lower(username)` (globally, like `email` — one person, one credential, one school, see below) and shape-constrained to `^[a-z0-9._-]{3,64}$` so `lower()` is a true identity; `users_credential_complete` ties `username` and `password_hash` together (both null or both set). `last_login_at` **re-adds a column the 2026-09-11 dead-schema cleanup dropped** for having no writer — it has one now (`repo.RecordLoginSuccess`), and this note exists so a future cleanup pass doesn't drop it again for the same reason. `failed_login_count` / `locked_until` back a lockout: past `LOGIN_MAX_FAILURES` consecutive failures the account is locked until `locked_until`, whatever the password.

**Why `users` is not tenant-scoped, restated.** `00001`'s original comment read *"Deliberately NOT tenant-scoped: one person may teach at two schools and must keep a single credential."* That reasoning is now **reversed by policy, not by schema**: a person is meant to work at exactly one school (below), so the multi-school justification is gone. `users` stays non-tenant-scoped anyway, because it is the credential table and isolation runs through `memberships` — the `tenant_isolation`-style policy on `users` (`00001:306-319`) depends on that shape, and rebuilding `users` as tenant-scoped would mean rebuilding that policy and the login path's pre-tenant lookup (below) from scratch for no behavioural gain.

**One person, one school.** `memberships_one_school_per_user` is a partial unique index on `memberships (user_id) where deleted_at is null and status <> 'revoked'` — a user may hold at most one active-or-invited membership at a time. Revoked memberships are excluded on purpose: a teacher who leaves one school must be able to join another, and a revoked row is history, not a live claim on the person. This index is what makes "does this user have more than one membership" impossible rather than merely unhandled, so the login path needs no picker and no tie-breaking rule.

**Role vocabulary.** `memberships.role`'s CHECK collapses from `('teacher','coordinator','director','admin','support')` to `('teacher','student','supervisor','admin')`. Existing `coordinator`/`director` rows become `supervisor`; `support` becomes `admin` — lossy (director-ness is not preserved), and expected to affect zero rows in every real environment, since nothing in Go or the UI ever wrote those values and the deleted demo seed only ever wrote `teacher`. All four roles are modelled — permission checks are written generically against `memberships.role` / `user_sessions.role` — but **only `role = 'teacher'` may complete a login today**; the other three exist so student and supervisor access can be turned on later by widening `domain.LoginEnabledRoles` alone, with no further schema change. `comment on table users` is rewritten to name the four roles and restate, deliberately, that `role = 'student'` may exist on a `memberships` row while no `students` row is ever linked to a `users` row — **students are not principals and have no login in this version**, full stop.

**The ordering problem and `user_sessions`.** At login there is no tenant yet — the tenant is the *result* of resolving a credential — and the same is true of every later request before its cookie is resolved to a session. Two tempting answers were rejected:
- **Connecting as the pool owner (`WithSystemTx`) is not the answer.** `internal/db/SPEC.md` already says *"never for request data"*, and resolving a cookie on every request is request data. It also does not do what its own old doc comment claimed: FORCE ROW LEVEL SECURITY binds the table owner too, so "connect as owner" does not bypass RLS on a FORCE'd table — it only ever worked on `jobs` because `jobs` carries no policy at all, and the fact it *appeared* to work for `users` was an artifact of the app actually connecting as the `postgres` superuser, contradicting `00001`'s own stated intent (see above).
- **A `security definer` function does not help either.** It is bound by FORCE the same way a plain connection is, unless its owner is a superuser or holds `BYPASSRLS` — so it would grant exactly the same full bypass through a narrower-looking door, while moving auth logic into PL/pgSQL in a codebase that otherwise keeps all of it in Go.

The actual answer is one narrow, explicit policy plus a transaction mode that never becomes a superuser:
```sql
create policy login_lookup on users
  using      (app.current_tenant_id() is null and current_setting('app.auth_lookup', true) = 'on')
  with check (app.current_tenant_id() is null and current_setting('app.auth_lookup', true) = 'on');
```
This is a second, *permissive* policy on `users` — permissive policies OR together, so it adds exactly one narrow door (no tenant set, and an explicit opt-in GUC) without touching what the existing `tenant_isolation`-shaped policy already allows. `internal/db.WithAuthTx` is the only code that sets `app.auth_lookup = 'on'`, and it still runs as `yanai_app`, never as owner — so a bug on the login path cannot read `students`, `tenants`, or anything else: every other tenant-scoped table's policy still evaluates `tenant_id = NULL` in that transaction and returns nothing.

**The identical policy is also needed on `memberships`, not just `users`** — caught by running the login flow end to end against a throwaway database, not by inspection. `internal/repo.ResolveMembership` learns *which tenant* to open a real session in by reading the user's `memberships` row, and `memberships` is `tenant_isolation`-scoped exactly like any other table via `app.enable_tenant_rls` — so without a matching `login_lookup` policy there, a `WithAuthTx` transaction (no tenant set) reads zero membership rows no matter what its query's `WHERE` clause says, and every login 403s `no_membership` even for a real account. Both policies are added and dropped together. `user_sessions` needs no equivalent policy because it carries **no RLS policy at all** — the same reasoning `jobs` already documents: the row must be readable before `app.current_tenant_id()` can be set, because resolving it is *how* the tenant becomes known. `tenant_id`, `membership_id` and `role` are denormalised onto each session row so that one pre-tenant read yields the whole context; the composite FK to `memberships (tenant_id, id)` still makes a cross-tenant session row impossible to insert, and the table only ever holds a token's sha256, never the token itself, so a row alone is not a usable credential.

`user_sessions.role` is re-checked against the live membership on every request (in `internal/httpapi.sessionAuth`, not here), so a role downgraded after login takes effect immediately instead of waiting for the session to expire.

**Pruning is opportunistic, not a job.** `internal/worker/SPEC.md` records that there is no ticker or scheduler in this codebase, so a `session.prune` job kind would have no enqueuer — the same mistake this repo made once already with an orphaned job kind. Expired rows are revoked lazily at validation time (`revoked_reason = 'expired'` / `'idle'`), and a best-effort sweep of long-expired rows runs inside the login transaction.

**Down is lossy in reverse.** `student` has no pre-`00002` equivalent (the down migration raises if any row holds it), and collapsing `supervisor` back to `coordinator` loses whether the row had been a `director`.
