## Purpose
The complete database schema as goose SQL migrations, applied against PostgreSQL 16 + pgvector. Currently one migration: the squashed baseline.

## Contents
- `00001_initial_schema.sql` — **the only migration.** The complete schema in one file: every table, view, function, trigger and RLS policy, in final form. Squashed twice (2026-08-26 from an 18-file history, 2026-09-10 from `00001`–`00009`), plus a third pass (2026-09-11) that deleted dead schema found by diffing every table/column against live Go and `yanai-ui` code rather than against migration history — see Change Log. Internally organised in the order the original files were, as section-comment banners, so history intuition about "which era added this" still roughly holds even though the file boundaries are gone. Nothing it creates is later dropped and nothing it creates is later altered: read it top to bottom and you have the schema — and, as of 2026-09-11, nothing it still creates goes unread by the application either, with the two documented exceptions in Resolved (`retake_authorizations`, `competency_year_snapshots`/`year_final_situations`).
- `ANALYSIS.md` — design notes: expected-painful queries, ambiguities in the original product mock, argued constraints. Predates both squashes; still valid as a design record, but it describes subsystems that no longer exist (the predictive `risk_*` tables, the per-session observations) and its object counts are historical. Its header carries the current live counts. That mock (`yanai-views.html`) no longer exists in the repo — see root `SPEC.md`.

## Inputs / Outputs
Applied with goose (`GOOSE_MIGRATION_DIR` points here in production). Downstream consumers: every Go package, `seed/seed_demo_tenant.sql`.

## Conventions & Constraints
- Migrations are schema only — seed/demo data lives in `seed/`, never here.
- **Append-only between squashes.** Never edit an applied migration: add a new numbered file (`00002_...` and up). `00001` is the squashed baseline and the one exception, and only under the conditions both squashes were done under — every environment's database can be dropped and re-created, so no `goose_db_version` row anywhere refers to a version the folder no longer has. A squash is not a routine edit: it is a deliberate act taken when the accumulated create-then-drop churn has made the chain harder to read than the schema it produces, and it is verified by diffing the catalog of a database built from the new baseline against one built from the old chain (see the 2026-09-10 entry for the method).
- **A migration must not create something a later migration drops, or alter something it just created** — that is the churn a squash exists to remove. Within a single new migration, write the final form directly.
- **A table or column with no Go or `yanai-ui` caller is a separate problem from churn, and is not caught by a squash** — a squash only removes objects a later migration in the chain itself dropped. Finding dead schema means diffing every table/column name against `internal/` and `yanai-ui/src`, not against migration history; see the 2026-09-11 Change Log entry for the method. Before dropping something that turns up dead, check whether it is deliberately-ahead-of-code scaffolding with a recorded reason to keep it (a Resolved entry, a dedicated comment, supporting constraints/indexes built only for it) rather than plain leftover — the two are not the same and get different answers.
- Text + CHECK "enums" in SQL are mirrored as constants in `internal/domain/consts.go` (cascade when adding values).
- Every tenant table gets FORCE ROW LEVEL SECURITY; `jobs` deliberately has no RLS (nullable tenant_id, workers span tenants).
- Column/table `comment on` strings are load-bearing documentation — keep them current.
- **Never write ` -- ` inside a SQL string literal.** goose strips everything after a double dash when deciding whether a line terminates a statement, even inside quotes, so a `comment on ... is '... -- ...';` swallows every statement after it until some later line happens to end in a semicolon outside a comment. It fails as `unexpected unfinished SQL query: ... missing semicolon?`. A migration carrying one can still appear to work, if a following statement happens to close the run-on — which is how three of them survived into the pre-squash chain undetected. The exception is inside a `-- +goose StatementBegin/End` block, where goose does not split on lines at all: `app.check_component_weights_sum()`'s `hint` string legitimately contains one. Everywhere else, punctuate with colons, commas or parentheses. Check with a quote-state scan of the file, not a plain grep, since the point is whether the `--` falls inside an open literal.

## Open Questions
- **The `kind` vocabulary change is not cascaded yet, and the seed is broken by it.** `seed/seed_demo_tenant.sql` writes `kind = 'quiz'` on five assessments and `kind = 'rubrica'` on one insert-select; both now violate `assessments_kind_check`, so the demo seed fails to apply against a freshly migrated database. `yanai-ui` (`src/lib/api/dto.ts`'s `AssessmentKind`, the dropdowns in `AddPracticeScoreDialog.svelte` and `class/[courseId]/evidence/new/+page.svelte`, the label map in `grades/[studentId]/+page.svelte`) still offers both values, so a teacher picking one gets a database rejection. Both were left out of the 2026-09-10 change on purpose — it was scoped to `migrations/` — and neither is a design question, only pending work. What *is* a question: which kind the existing uses should become (`practica`/`proyecto` and `examen`/`proyecto` were both considered and neither chosen), since nothing in the norm distinguishes them.
- `evaluation_criteria.performance_standard_id`'s capacidad is not checked against `evaluation_criteria.competency_id` — nothing stops linking a criterio to a desempeño that belongs to a different competencia. Every other cross-table consistency this strict in the schema is enforced by a trigger (e.g. `app.sync_score_denormalised`); this one is a known, deliberate gap pending a decision on whether it's worth one.

## Resolved
- *Should `note_summaries`/`note_summary_sources` be dropped now that nothing writes to them?* Reversed 2026-09-11 — **yes, dropped.** The 2026-08-29 answer below was "no, a real summary feature should fill them" (unchanged reasoning); asked again during the 2026-09-11 dead-schema pass, the decision came back the other way: nothing had written a row in the interim either, and re-adding two tables with whatever feature eventually needs them costs less than carrying unused schema in the meantime. See the 2026-09-11 Change Log entry.
- *Should `competency_year_snapshots`/`year_final_situations` be dropped now that nothing writes to them?* No — unchanged by the 2026-09-11 pass, which deliberately left this pair alone. They are the normative year-end acta records RVM 094-2020 5.1.3 requires, lost their writer only because `internal/promotion` was removed (2026-08-27), and whoever restores year-end close should write to them.
- *Is MINEDU's "B — En proceso" a pass?* (was: `passing_value` and `is_passing` disagreeing in the seed). The question was mis-posed. Under RVM 048-2024 "aprobado" is not a property of a level at all: an área counts as approved only "si cumple las condiciones establecidas en la tabla que dispone las condiciones de promoción o permanencia" (Anexo 09), and that table makes B sufficient in 1.°/3.°/4.° and insufficient in 2.°/5.°. The cutoff both columns encoded — nota 11 — comes from Anexo 07, which governed the 2020 school year only and expired when transitoria 8.3 extended the literal scale to all of Secundaria on 1 March 2021. `00018` therefore documented both columns as advisory, and `internal/promotion` (since removed, 2026-08-27) decided promotion by counting levels per área.
