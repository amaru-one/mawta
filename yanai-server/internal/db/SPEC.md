## Purpose
The pgx connection pool and the per-transaction tenant/RLS discipline, plus error mapping to HTTP-shaped app errors.

## Contents
- `db.go` — `DB` (pool wrapper), `Open`/`Close`, `TenantCtx{TenantID, ActorID, TeacherID, RequestID, Role}`, `WithTenantTx` (SET LOCAL role `yanai_app` + GUCs `app.tenant_id`/`app.actor_id`/`app.request_id`, so context evaporates at commit/rollback), `WithAuthTx` (SET LOCAL role `yanai_app` + `app.auth_lookup='on'`, no tenant — the pre-tenant login/session lookup path, via `users`' and `memberships`' matching narrow `login_lookup` policies and `user_sessions`' lack of any policy), `WithSystemTx` (the pool's own connection role, no role drop, no GUCs — see Conventions for what that means in practice).
- `errors.go` — `AppError{Status, Code, Message}`, `NewAppError`, `MapError` translating pgx/Postgres errors (not-found, unique violations, check violations, RLS denials) into app errors.

## Inputs / Outputs
Input: `DATABASE_URL` (`cmd/api`, connects as the non-owner `yanai_app` role) or `ADMIN_DATABASE_URL` (`cmd/useradd`, connects as the `postgres` superuser/owner — see `internal/config/SPEC.md`). Output: transactions handed to `repo`, `httpapi`, and `worker` callbacks; `AppError` consumed by `httpapi/respond.go`.

## Conventions & Constraints
- All tenant data access goes through `WithTenantTx`; never run tenant queries on the raw pool.
- **`WithSystemTx` runs as whatever role the pool connected as — its reach is entirely a property of the caller's `DATABASE_URL`/`ADMIN_DATABASE_URL`, not of this function.** `FORCE ROW LEVEL SECURITY` (used by every table `app.enable_tenant_rls` touches, and by `users`) binds a non-superuser table owner just as it binds anyone else — so a `WithSystemTx` call from `cmd/api`'s pool (connected as `yanai_app`) reaches only `jobs`, the one table with no RLS policy at all, exactly as the worker's nil-tenant job dispatch needs. A `WithSystemTx` call from `cmd/useradd`'s pool (connected as the `postgres` superuser via `ADMIN_DATABASE_URL`) reaches `users` and `memberships` too — superusers bypass row security unconditionally, FORCE included — which is exactly what seeding the first account in an empty tenant needs. **Never for request data**, regardless of which pool calls it: `cmd/api` never opens `ADMIN_DATABASE_URL` at all, so this distinction is enforced by which binary has which connection string, not by a runtime check.
- **`WithAuthTx` is the pre-tenant exception to the "go through `WithTenantTx`" rule**, for real authentication (`migrations/00001_initial_schema.sql`). At login, and at every session-cookie validation, there is no tenant yet — the tenant is the *result* of resolving a credential or a token — so neither lookup can go through `WithTenantTx`. `WithAuthTx` still drops to the non-owner `yanai_app` role (unlike `WithSystemTx`) and sets no tenant, only `app.auth_lookup='on'`; that GUC is read by two matching `login_lookup` policies, on `users` and on `memberships` (login needs both: which credential matched, then which tenant/role its membership names), so this mode can reach those two tables (narrowly) and `user_sessions` (which has no policy, for the same reason `jobs` doesn't) and nothing else — every other tenant table's policy evaluates `tenant_id = NULL` here and returns zero rows. A `security definer` function was considered instead and rejected: it is bound by FORCE the same way a plain connection is, so it would need a superuser owner and would grant a full bypass, not a narrow one. Used only by `internal/repo/auth.go`.
- A zero `ActorID` means system/job actor (empty `app.actor_id`). `TenantCtx.Role` is empty for the same case; it is set from the resolved `user_sessions.role` for a real request.
