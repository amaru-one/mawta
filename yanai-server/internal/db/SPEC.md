## Purpose
The pgx connection pool and the per-transaction tenant/RLS discipline, plus error mapping to HTTP-shaped app errors.

## Contents
- `db.go` — `DB` (pool wrapper), `Open`/`Close`, `TenantCtx{TenantID, ActorID, TeacherID, RequestID, Role}`, `WithTenantTx` (SET LOCAL role `yanai_app` + GUCs `app.tenant_id`/`app.actor_id`/`app.request_id`, so context evaporates at commit/rollback), `WithAuthTx` (SET LOCAL role `yanai_app` + `app.auth_lookup='on'`, no tenant — the pre-tenant login/session lookup path, via `users`' and `memberships`' matching narrow `login_lookup` policies and `user_sessions`' lack of any policy), `WithSystemTx` (the pool's own connection role, no role drop, no GUCs — cross-tenant maintenance only, see the correction below).
- `errors.go` — `AppError{Status, Code, Message}`, `NewAppError`, `MapError` translating pgx/Postgres errors (not-found, unique violations, check violations, RLS denials) into app errors.

## Inputs / Outputs
Input: `DATABASE_URL`. Output: transactions handed to `repo`, `httpapi`, and `worker` callbacks; `AppError` consumed by `httpapi/respond.go`.

## Conventions & Constraints
- All tenant data access goes through `WithTenantTx`; never run tenant queries on the raw pool.
- **`WithSystemTx` does not "bypass RLS" as a general property — this file used to claim it did, and that was wrong.** `FORCE ROW LEVEL SECURITY` (used by every table `app.enable_tenant_rls` touches, and by `users`) binds the table owner too, so connecting as the owner does not skip policies on those tables. `WithSystemTx` reaches `jobs` only because `jobs` carries no RLS policy at all — there is nothing to bypass. Whatever additional cross-tenant power it appears to have today is an artifact of `DATABASE_URL` actually connecting as the `postgres` superuser rather than as a dedicated login role that `SET ROLE`s to `yanai_app` (see `migrations/SPEC.md`'s Open Questions) — do not design anything that depends on that being true. It is only for genuinely cross-tenant work (the worker's dispatch of a nil-tenant job — there is no ticker or scheduler, see `internal/worker/SPEC.md`) — **never for request data.**
- **`WithAuthTx` is the pre-tenant exception to that rule**, added for real authentication (`migrations/00002_auth.sql`). At login, and at every session-cookie validation, there is no tenant yet — the tenant is the *result* of resolving a credential or a token — so neither lookup can go through `WithTenantTx`. `WithAuthTx` still drops to the non-owner `yanai_app` role (unlike `WithSystemTx`) and sets no tenant, only `app.auth_lookup='on'`; that GUC is read by two matching `login_lookup` policies, on `users` and on `memberships` (login needs both: which credential matched, then which tenant/role its membership names), so this mode can reach those two tables (narrowly) and `user_sessions` (which has no policy, for the same reason `jobs` doesn't) and nothing else — every other tenant table's policy evaluates `tenant_id = NULL` here and returns zero rows. The `memberships` half was missing in an early pass and caught only by running the actual login flow end to end (every real account 403'd `no_membership`) — a reminder that an RLS design this narrow has to be exercised, not just reasoned about. A `security definer` function was considered instead and rejected: it is bound by FORCE the same way a plain connection is, so it would need a superuser owner and would grant a full bypass, not a narrow one. Used only by `internal/repo/auth.go`.
- A zero `ActorID` means system/job actor (empty `app.actor_id`). `TenantCtx.Role` is empty for the same case; it is set from the resolved `user_sessions.role` for a real request.
