## Purpose
The chi router, middleware, and HTTP handlers — one handler file per screen of the app. Handlers parse/validate, open a tenant transaction, call `repo`, enqueue jobs, and log events; SQL lives in `repo`.

## Contents
- `router.go` — `API` struct, `New`, `Router()`. `/healthz` and `POST /auth/login`/`POST /auth/logout` are public; every other `/api/v1/*` route sits in an `r.Group` behind `sessionAuth` (its own group because chi panics on `Use()` after routes are already registered on the router), `handleHealthz`.
- `middleware.go` — `requestID`, `requestLogger`, `sessionAuth` (resolves the session cookie via `db.WithAuthTx`, enforces absolute/idle expiry and the role gate, then resolves the teacher exactly as the old `tenantAuth` did, inside a real tenant transaction; builds `db.TenantCtx`), `tenantCtxFrom`.
- `auth.go` — `handleLogin`, `handleLogout`, `setSessionCookie`/`clearSessionCookie`, `sessionTokenFrom`. See Conventions below for the full login sequence and its error codes.
- `home.go` — GET /home, date resolution in tenant timezone. The response is the teacher's agenda: `today` (dated sessions with `room`/`topic`) and `week` (the rest of the ISO week as `{date, weekday, sessions}` days). `?date=` moves both.
- `common.go` — GET /me (carries `tenant.uses_internal_grading`, the school's own-system switch).
- `class.go` — GET class dashboard, POST session start.
- `session.go` — GET session roster, PUT attendance, POST mark-all-present, voice-note create/audio/save/discard. Save confirms the note exists (there is no per-row state left to write); discard is a real soft delete (`deleted_at`), `204`. Create enqueues `voice_note.transcribe` (`enqueueVoiceNoteTranscribe`) in the same transaction as the insert. There is no per-session observation surface, and nothing in the app is risk-driven.
- `grades.go` — GET student grades, GET grading components, POST assessment (optional `student_id` scopes it to one student, optional `criterion_ids` links the criterios it evidences, optional `counts_toward_internal` keeps it out of the school's own average), POST assessment delete (soft; requeues every affected student for recompute), POST score create/correct (numeric mark only, both enqueue `grade.recompute`, which chains nothing), POST criterion-score create/correct (a mark — numeric or ordinal by level — against one criterio within an assessment), `enqueueGradeRecompute` helper.
- `competencies.go` — the official MINEDU record: GET competencies for a student (level, whether a conclusión descriptiva is mandatory and why — there is deliberately no suggested level), POST competency-level (the only writer of an official nivel de logro), POST conclusion.
- `criteria.go` — the criterios de evaluación, **authoring only**: GET/POST class competency capabilities (the capacidades a criterio anchors to), GET class criteria, POST criterion (the teacher writes their own, anchored to a capacidad of the same competencia), POST criterion delete. There is deliberately no nivel-de-logro route here: a criterio tags a piece of evidencia, it is not the thing officially judged. Per-evidence marks against a criterio live on the criterion-score routes in `grades.go`.
- `students.go` — the two reads the evaluating screens are built on: `GET /classes/{classID}/students?competency_id=&term_id=` (the roster with each student's level in one competencia and its evidence count) and `GET /classes/{classID}/students/{studentID}/evidence?competency_id=&term_id=` (that student's evidence for the period, narrowed through the criterio tags). `competency_id` is optional on both — a class with no competencias configured still has a roster, which is a more useful answer than an error.
- `practice_scores.go` — POST create / POST delete unofficial practice scores.
- `notifications.go` — list, mark read, read-all.
- `profile.go` — GET /profile.
- `params.go` — path/query parsing helpers and error shorthand. `respond.go` — `writeJSON`/`writeError`/`writeAppError`.

## Inputs / Outputs
Inputs: HTTP requests carrying the `yanai_session` HttpOnly cookie (set by `POST /auth/login`). Outputs: JSON responses (snake_case, RFC3339 timestamps, empty lists as null); rows via `repo`; jobs via `repo.EnqueueJob` in the same transaction as the triggering write; audit events via `repo.LogEvent`/`LogStudentReads`.

## Conventions & Constraints
- One tenant transaction per request via `a.db.WithTenantTx`; enqueue + event-log inside it so they're atomic with the write.
- Every response returning identifiable student rows must log `student.read` events (`repo.LogStudentReads`).
- Route changes cascade to the UI's `src/lib/api/endpoints/`.
- Handlers contain no SQL — queries belong in `internal/repo`.
- **No route records a *nivel de logro* for a criterio, and none may be added.** The criterio is the ruler, never the official judgement (RVM 094-2020, 5.1.1.3 p.3); the only nivel-de-logro route is `POST /classes/{classID}/students/{studentID}/competency-levels`.
  This does not forbid marking evidence against a criterio. `POST /assessments/{assessmentID}/criterion-scores` and `POST /criterion-scores/{criterionScoreID}/correct` exist and are meant to: they record a per-evidence mark, numeric or ordinal by level, inside one assessment. That mark is evidence and never rolls up into a competency level. Read as a blanket ban, the earlier wording contradicted the Contents section above, the `value_scale` rule below, and the routes themselves — and, under the spec-wins rule in `AGENTS.md`, told a reader to delete working behaviour.
- **`value_scale` decides what a score may carry.** `handleCreateAssessment` accepts `numeric` (requires a positive `max_score`) or `rubric` (rejects a `max_score`); a rubric assessment has `counts_toward_internal` forced false server-side, since it carries no overall mark a weighted average could use. `handleCreateScore`/`handleCorrectScore` accept `raw_value` only — a numeric mark against the assessment's own scale. Per-criterio marks (numeric or ordinal by level, validated against AD/A/B/C) go through `handleCreateCriterionScore`/`handleCorrectCriterionScore` instead, never through the score routes.
- A nivel de logro is only ever written from an explicit teacher action. No handler may derive one from `computed_grades`; `AssertCompetencyLevel` leaves `suggested_level_id` and `computed_grade_id` null on purpose (RVM 094-2020, 5.1.1.3 p.2-3) — see `internal/repo/SPEC.md`.
- Whether a conclusión descriptiva is mandatory is derived server-side from the student's live level, never taken from the request body.
- **`handleLogin` sequence and why each step is ordered where it is:** decode → lowercase the username → `repo.FindLoginCandidate` via `db.WithAuthTx` (on no match, still call `auth.VerifyPassword` against `auth.DummyHash()` so a missing username takes the same time as a wrong password) → `locked_until` in the future → `account_locked` (429) → non-`active` status → `invalid_credentials`, the *same* code a wrong password gets, so account state never leaks → verify the password (a failure is recorded in its own `WithAuthTx`, separate from the read, so a later rollback can't lose the counter) → `repo.ResolveMembership` → the role gate against `domain.LoginEnabledRoles`, checked **after** the password specifically so it cannot be used as a role/username enumeration oracle (`role_not_enabled`, 403) → `repo.ResolveTeacher` in a real `WithTenantTx` (`not_a_teacher_profile`, 403, if absent) → mint the token, `repo.CreateSession`, `repo.RecordLoginSuccess`, opportunistic `repo.PruneSessions` (all in one final `WithAuthTx`) → set the cookie → return the same shape `GET /me` does (there is no separate probe endpoint — `GET /me` already 401s once `sessionAuth` is in place, so it doubles as the session check the UI's root layout already calls first).
- **Failed logins are `slog`-only, not `events`.** `events` is tenant-RLS'd, and a failed login for an unknown username has no tenant to log under. `slog.Info` carries the username, request id and reason, never the password. A successful login writes `auth.login` to `events` inside the tenant transaction, via `repo.LogEvent`, exactly like any other audited write.
- **Session cookie is not rotated per request** — only minted on login. `+layout.svelte` fires `getMe()` and the notification poll concurrently; per-request rotation would have one invalidate the other's cookie and produce intermittent, hard-to-reproduce logouts.
- **Two transactions per authenticated request**, up from one: `sessionAuth`'s `WithAuthTx` (resolve the session, throttled `TouchSession`) then a `WithTenantTx` (resolve the teacher, run the handler). This is the direct cost of the ordering problem — the tenant cannot be known before the session is — and is deliberate; see `internal/db/SPEC.md`.
- Error codes introduced for auth: `missing_session`, `invalid_session`, `session_expired` (401, and each clears the cookie), `invalid_credentials`, `account_locked` (429), `role_not_enabled`, `no_membership`, `not_a_teacher_profile` (403). `not_a_member` (403) is the same condition the old `tenantAuth` checked, kept under its old name. Retired: `missing_tenant`, `missing_actor`.

## Open Questions
- **`yanai-ui` is stale on the discard contract, on purpose.** `POST /voice-notes/{voiceNoteID}/discard` responds `204`, but `yanai-ui`'s `discardVoiceNote()` still types its return as `Promise<{status: VoiceNoteStatus}>`. This is not a functional break today: the client already ignores the resolved value (`removeNote()` in `lesson.ts` never reads it), and `client.ts`'s `request()` already treats any `204` as `undefined`. Whoever next touches voice notes on the frontend should close this gap rather than assume it was missed.
- **`yanai-ui` is stale on `value_scale`.** `yanai-ui`'s `dto.ts` types `ValueScale` as `'numeric' | 'ordinal'`; the routes above accept `'numeric' | 'rubric'`. Whoever next touches assessments on the frontend should close this gap. Note `'ordinal'` is the `criterion_scores` scale, not an assessment scale — the two were being conflated.
- **`yanai-ui` still carries the superseded "a criterio is never graded" wording** in `src/lib/api/endpoints/SPEC.md` and `src/routes/class/[courseId]/criteria/SPEC.md`, the latter contradicting itself within one file. It was left untouched deliberately: `yanai-ui` is out of scope for the current stage of work. Whoever next works in the UI should apply the rescoping above.
- **The criterion-score routes have no client.** `handleCreateCriterionScore`/`handleCorrectCriterionScore` are reachable, constrained and audited, but `yanai-ui/src/lib/api/endpoints/criteria.ts` exposes only `getClassCriteria`, `createCriterion` and `deleteCriterion`. Build the client or retire the routes — but decide, rather than leaving server capability with no consumer.
